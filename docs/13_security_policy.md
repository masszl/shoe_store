# День 13. Защита базы данных «Чудо Обувь»

## SQL-инъекции

Нельзя подставлять пользовательский ввод в SQL через f-строки. Уязвимый пример: `f"SELECT * FROM users WHERE login = '{login}'"`. Исправление: `conn.execute("SELECT * FROM users WHERE login = ?", (login,))`. В `security_demo.py` демонстрируется инъекция `' OR '1'='1` только для чтения данных. Безопасный вариант возвращает ноль совпадений.

## Примеры параметризации

1. Вход: `SELECT * FROM users WHERE login = ?`, `(login,)`.
2. Поиск товара: `SELECT product_id, name FROM products WHERE name LIKE ?`, `(f"%{text}%",)`.
3. Регистрация: `INSERT INTO users (last_name, first_name, login, role_id, password_hash) VALUES (?, ?, ?, ?, ?)`, значения передаются отдельным кортежем.

В существующих файлах проекта также необходимо проверить все динамически собранные SQL-запросы и заменить небезопасные места, если они есть.

## Пароли

По учебному заданию используется SHA-256 (`hashlib.sha256`). Пароли в открытом виде не сохраняются, сравниваются хэши. **Для реального приложения SHA-256 без соли недостаточно:** нужен Argon2id, scrypt или PBKDF2 с индивидуальной солью.

## Разграничение прав

`admin_db` имеет полный набор операций, `developer` — чтение и изменение данных, `reader` — только чтение. Проверки реализуются на уровне приложения. Прямой доступ к файлу БД следует ограничить правами файловой системы.

## Аудит

Таблица `login_audit` хранит логин, статус успешного/неуспешного входа и время попытки. Таблица `audit_log` из Дня 11 хранит изменения цен и удаление заказов.

## Защита файла

В Windows ограничить доступ к `database.db` через вкладку «Безопасность» в свойствах файла, не публиковать реальные базы и бэкапы в GitHub. Для Linux возможны права `chmod 600`.
